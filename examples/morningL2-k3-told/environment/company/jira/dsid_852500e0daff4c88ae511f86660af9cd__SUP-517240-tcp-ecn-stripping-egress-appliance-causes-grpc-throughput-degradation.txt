ECN bits stripped by customer egress appliance causing gRPC throughput degradation and long-tail streaming latency on private deploy

Customers on a Private deployment report intermittent long-tail latency and throughput degradation for streaming gRPC requests and large artifact downloads. Traffic traces from the customer's egress appliance show ECN (Explicit Congestion Notification) marking/ECT bits being stripped/re-written rather than preserved, causing the TCP sender in our serving nodes to fall back to conservative congestion control behavior and frequent slow-start events. The issue is most visible during large KV cache warm-ups and sharded model downloads where sustained throughput matters.
FinEdge observed 95th and 99th percentile streaming latencies increase by 3–6x during busy periods; multiple user requests experienced stalls of 5–20s. Some model shard downloads reported partial content throughput degradation causing backend 503s when cache misses overlapped with reduced TCP throughput. No user data leak; availability remained degraded for affected flows.
1) Deploy a private Redwood agent inside FinEdge VPC (prod-us-east).
2) Trigger concurrent streaming generation jobs that produce steady token output (>200 KB/s sustained per stream) across ~20 clients to simulate warm cache and shard download traffic.
3) Run tcpdump on serving node and on the customer egress appliance for the same 1-minute window capturing first SYN packets and some data packets (flags + IP TOS/ECN bits).
4) Compare ECT/CE bits on packets leaving serving node vs packets observed leaving appliance to internet.

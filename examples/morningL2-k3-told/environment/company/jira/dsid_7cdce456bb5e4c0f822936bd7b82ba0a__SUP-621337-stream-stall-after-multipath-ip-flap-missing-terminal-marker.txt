Intermittent stream stall after upstream multipath IP flap - final event never delivered to client

Issue summary: Customer reports repeated requests where an open websocket/SSE stream completes generation server-side but the client never receives the terminal/end event or final token. The connection closes from the edge with no terminal message and the client sees an 'incomplete' final choice. Impact: Several production customers on Dedicated have brief but recurring user-visible partial outputs in the last 1-3 tokens. This breaks downstream parsers and creates incorrect UI states (spinners that never finish). Frequency: ~1–3 occurrences per day across a subset of sessions using the customer's dedicated pool. Environment: Customer on Dedicated capacity in us-east behind our managed edge-proxy and a load-balancer that performs multipath routing for egress. Observed behavior: - Generation completes on serving-hosts (trace shows final EmitChoice/END record) - Edge/proxy closes TCP connection to client with FIN before END event is reliably delivered to client library - Client SDK receives truncated stream or EOF without terminal event; does not trigger resume because resume token is missing/never exposed - No obvious 5xx in upstream logs, edge shows connection close reason: RST (or half-close) in proxied path
1) Use customer workload (long chat generation ~400 tokens) on dedicated pool behind edge-proxy multipath routing
2) Run with intermittent simulated path swap (network flapping / multipath change) from test LB
3) Observe client receives stream but occasionally never gets terminal event despite backend EmitChoice logged
4) Reproduce more reliably by enabling short-lived path churn (curl or websocket test harness behind LB)

Initial hypothesis: Edge/load-balancer multipath switch triggers a TCP teardown on one path while backend continues to produce final tokens on another; the atomicity of our 'finalization' event is lost if the edge does not forward the last chunk before issuing FIN. Evidence: edge proxy logs show FIN close prior to final ACK from upstream in ~60% of samples for affected sessions. The serving runtime consistently logs END/Emit events. Additional hypothesis: client SDK's resume logic requires a terminal marker or a resume-token emitted in-stream; if the terminal marker is missing the SDK treats the session as a hard EOF and does not call 'resume' flow. Tests: repeated reproduce with synthetic path churn produced same symptom within 30 minutes. Edge team reproduced local harness when forcing half-close ordering. Related to previously observed edge keepalive/coalescing timing (see linked SUP-842117). Potential fixes: - ensure edge buffers and flushes terminal chunk before initiating close (drain window) - add idempotent terminal marker persisted to stream metadata so resume can detect missing terminal and request a replay - adjust SDK to attempt resume when last-seen sequence < final-expected and connection closed without end marker
1) Customer can enable websocket sticky session to reduce multipath rebinds in LB configuration (recommended for now)
2) Increase keepalive window on edge-proxy to avoid immediate close during path swap
3) For critical clients, enable structured end-marker in request metadata (if available) so client can attempt resume on missing marker

IdP claim rename causes service-proxy session validation failures for internal analytics portal

Summary: Multiple employees report immediate 401/403 when accessing the internal analytics portal web UI and CLI flows after a planned OKTA profile attribute rename rollover. The IdP attribute 'departmentCode' was renamed to 'dept_code' in a scheduled change; some downstream components reject sessions that contain the old claim name.

Background: We rolled a non-breaking claim mapping change on 2026-03-09 at 03:00 UTC intended to standardize claim names across services. Most services were updated in the mapping table, but the identity-proxy service still validates session cookies by expecting the legacy claim name. This results in signature validation success but claim parsing fails and the proxy returns 401 for affected users.
~120 unique sign-ins across SSO tracked as failures in last 6 hours. Several oncall engineers and product users cannot access analytics dashboards; internal scheduled jobs that fetch metrics via the internal-cli are failing. Potentially blocks incident response and data analysis during business hours.
1) Use a user account with Okta profile that had departmentCode populated. 2) Authenticate via SSO into console.redwood.internal. 3) Observe redirect to analytics-portal and 401 from identity-proxy; CLI login flows (redwood-cli auth login) return 'session validation failed: missing required claim' error. 4) Capture auth header and inspect JWT claims: old claim name present in some tokens, new claim name in others.
identity-proxy.log excerpt (2026-03-10T09:12:34Z): "ERROR session_validation: missing expected claim 'dept_code' for user jdoe@redwood.com; raw_claims: {"departmentCode":"ENG-2"}"
analytics-portal nginx access: 401 responses correlated to requests with cookie session_id=xxxx.
Auth service issued tokens: some tokens include both claims for a short transitional window; others only include departmentCode. No token signature errors.
- Confirmed Okta mapping change executed at 2026-03-09 03:00 UTC. - Deployment inventories show identity-proxy config not updated during the rollout (stale config entry). - Proxy code defensively validates presence of 'dept_code' only; it treats missing claim as authentication error. - Edge case: tokens minted by older auth cache include 'departmentCode' only; new mint includes 'dept_code'. - Hypothesis: staggered rollout and a long-lived auth-cache produced mixed tokens leading to validation failures. - Quick check: restarting identity-proxy with updated mapping fixes parsing for web logins but some CLI tokens remain rejected due to token caching at CLI gateway layer.
- Short term: restart identity-proxy nodes to accept legacy claim name (degraded but restores access). - Evict auth-cache entries for tokens minted before mapping change. - Instruct CLI users to run 'redwood-cli auth logout' and re-login to get fresh tokens.

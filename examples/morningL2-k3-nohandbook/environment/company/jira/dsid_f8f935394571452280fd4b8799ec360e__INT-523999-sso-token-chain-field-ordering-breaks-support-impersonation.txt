SSO token-chain field ordering causes support impersonation to return sessions with no RBAC roles

Intermittent occurrences where JIT 'Impersonate as user' shows 'Granted' in UI but resulting sessions lack RBAC roles, blocking access to runbooks and on-call tools.
Issue summary: After an Okta device-trust reauth and a recent group-merge for some users, the support impersonation flow intermittently returns a token chain where the order of 'aud' and 'azp' claims is swapped. Impact: Support engineers are unable to successfully impersonate affected users — the Support Console marks the action as 'Granted' but the resulting session has an empty role list and receives 403s from runbook APIs. Scope: Approximately 10-15 support users in prod-us-west affected since 2026-03-11 22:30 UTC.
1) Trigger Okta reauthentication for a user that was moved between groups (group-merge event).
2) In the Support Console, click 'Impersonate' on that user and accept the JIT approval link, if prompted.
3) Observe the UI shows 'Granted' immediately but background API calls to /runbooks and /oncall endpoints return 403 and role lookup shows empty list.
4) Inspect identity-proxy logs for the token_chain that was used to establish the impersonated session and check claim ordering.
Impersonation recorded as Granted but sessions have no RBAC roles. Identity-proxy logs show token_chain with claims ordering like [sub, azp, aud, groups] rather than the previously expected [sub, aud, azp, groups]. Role resolution step returns an empty list and downstream calls fail with 403.
Impersonation should produce a session that inherits the user's RBAC groups so that support-runner and runbooks are accessible. Claim ordering in token_chain should not affect role resolution.

Initial hypothesis: token-chain parsing in identity-proxy assumed a stable claim iteration order and built the session_package by consuming claims in sequence; when 'azp' appeared before 'aud' the code path omitted aud->service mapping and left roles empty.
Reproduced locally with a crafted token fixture where azp precedes aud; identity-proxy returned session with roles=[] and support-runner API returned 403.
SRE applied a temporary cache clear on prod identity-proxy instances in us-west which restored impersonation for ~75% of affected users immediately.
Code review: PR #892 (identity-proxy) introduced a token-chain serializer that iterates a JSON map; map iteration order is not guaranteed and unit tests did not include permutations of claim ordering.

Hotfix: identity-proxy cache cleared and a small parsing fix deployed to normalize token_chain claim ordering at parse-time (identity-proxy v1.14.3). Workaround for affected engineers: re-provision SCIM entry for the user or perform a full re-login to Okta to get a fresh token.

Geo cutover: variant affinity mismatch causes split request routing for dedicated tenant

Issue summary: During a scheduled geo cutover for a dedicated customer (Peregrine HealthTech) we observed a subset of requests from the tenant being routed to a legacy variant despite an explicit model version pin. Impact: ~12% of requests for the tenant in us-west were answered by redwood-chat-v2.1-legacy (legacy weights) resulting in higher latency and tokenization mismatch with customer post-processing, causing errors in their pipeline. Environment: Production dedicated cluster (us-west) on committed capacity. Canary weight adjustment and region handoff occurred as part of a planned cutover at 2026-03-10T03:00Z. Observed behavior: After the cutover we see session-level split routing: some streams maintain the pinned variant while others are diverted to an older variant. Expected behavior: Tenant-level explicit pin should ensure steady routing to pinned model across the cutover window. This ticket captures investigation, intermediate findings, and proposed mitigations.
1) Customer created an explicit model pin for tenant T-234 to redwood-chat-v2.1.
2) Scheduled geo cutover (us-west primary -> us-east warm) with canary weight ramp described in runbook.
3) Triggered cutover at 2026-03-10T03:00Z.
4) Observe that ~12% of requests post-cutover return responses generated by redwood-chat-v2.1-legacy while rest use pinned variant.
5) Attempts to repro with replayed traffic from tracing show same split when requests arrive through the edge pool that drained last.

Timeline: 03:00 cutover start. 03:02 first split observed in edge logs. Hypothesis A: edge-proxy drain/reshard left behind sessions tied to older routing snapshot, causing stale affinity to prev variant. Hypothesis B: commit for explicit pin was applied to control-plane snapshot after some edge nodes adopted the new routing epoch, leading to inconsistent snapshot visibility. Evidence: session-handoff warnings show stale-session-pin=true on az3 nodes. Control-plane snapshots at 03:01 and 03:03 indicate pin present in later snapshot only. We replayed traffic through a warmed & drained edge pool and observed deterministic split correlated with node epoch. Additional logs point to KV cache population differences between v2.1 and v2.1-legacy which can allow selection logic on edge to fall back when a prefix is missing. Related PRs include an edge-agent change to snapshot refresh timing (PR 411). Initial impact mitigation: increased canary stabilization delay in runbook and triggered an on-demand pin-refresh broadcast to all edge instances. Ongoing: SRE to validate snapshot propagation guarantees and add quorum commit before canary weight shift. Control-plane team investigating commit-ordering and snapshot TTL handling.

Workaround applied: broadcasted pin-refresh and temporarily blocked canary weight ramp until pin commit quorum reached; customer errors reduced to acceptable levels. Root cause: race between control-plane pin commit and canary weight change combined with edge snapshot refresh timing that allowed some edge nodes to evaluate routing using an older snapshot. Permanent fix in progress: (1) control-plane will require commit-ack quorum before allowing canary weight adjustments (PR tracked in orchestrator#2087), (2) edge-agent will be updated to perform topology-aware snapshot pulls during cutovers to avoid stale session affinity, (3) add test coverage in cutover e2e tests for explicit-pin + geo handoff scenarios. Follow-ups: schedule postmortem with Runbook/Release owners, update geo-cutover playbook with explicit pin verification step, and run a dedicated chaos test for snapshot-loss scenarios. Targeted rollout of fixes in next release window (2026-03-26).
